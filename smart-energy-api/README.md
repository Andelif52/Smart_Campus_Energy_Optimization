# Smart Campus Energy Optimization API

BUP CSE Fest 2026 Hackathon Solution

An AI-assisted energy optimization API that interprets campus operator instructions, validates them, and generates an optimized 24-hour battery, solar, and grid schedule.

---

# Overview

This system accepts:

- Campus energy demand forecast
- Solar generation forecast
- Electricity tariff information
- Battery configuration
- Natural language operator notes

The system converts operator notes into structured energy directives using an LLM, validates those directives using deterministic guardrails, and applies them to an optimization model.

The complete workflow:

```
Energy Scenario
      |
      v
LLM Operator Note Interpreter
      |
      v
Directive Validation / Guardrails
      |
      v
Energy Optimization Solver
      |
      v
Final Schedule Validation
      |
      v
Optimization API Response
```

The LLM is used only for understanding operator notes. The final energy scheduling decisions are generated by the deterministic optimization layer.

# Supported Energy Directives

The API supports the following operator instructions.

## 1. Solar Reduction

Reduces available solar generation during specified hours.

Example:

```
Solar generation will be reduced to 50% from 12 PM to 2 PM.
```

Generated directive:

```json
{
  "directive_type": "solar_reduction",
  "structured_adjustment": {
    "hours": [12, 13],
    "factor": 0.5
  }
}
```

---

## 2. Minimum Battery Reserve

Keeps battery energy above a required minimum level.

Example:

```
Keep at least 100 kWh in the battery from 6 PM to 9 PM.
```

Percentage-based instructions are converted into battery energy values.

Example:

```
Keep the battery at least 50% full.
```

For a 200 kWh battery:

```
50% = 100 kWh minimum reserve
```

---

## 3. No Charge Window

Prevents battery charging during specified hours.

Example:

```
Do not charge the battery from 2 PM to 4 PM.
```

---

## 4. No Discharge Window

Prevents battery discharge during specified hours.

Example:

```
Do not discharge the battery during peak hours.
```

---

## 5. Maximum Grid Import Window

Limits grid usage during specified hours.

Example:

```
Grid usage must stay below 50 kWh between 6 PM and 8 PM.
```

---

## 6. No Operation

Notes unrelated to energy scheduling are ignored.

Example:

```
The cafeteria will close tomorrow.
```

Result:

```json
{
  "directive_type": "no_op",
  "applies": false,
  "structured_adjustment": null
}
```

# Optimize Energy

## POST `/optimize-energy`

The endpoint accepts:

- Scenario ID
- Battery configuration
- 24-hour forecast data
- Operator notes

Example:

```json
{
  "scenario_id": "campus_demo_001",
  "operator_notes": [
    "Do not charge the battery from 2 PM to 4 PM.",
    "Solar generation is reduced by 50% from 12 PM to 2 PM."
  ],
  "battery": {
    "capacity_kwh": 200,
    "initial_energy_kwh": 100,
    "minimum_energy_kwh": 20,
    "max_charge_kwh_per_hour": 50,
    "max_discharge_kwh_per_hour": 50
  },
  "hours": [
    "... 24 hourly entries from hour 0 to hour 23 ..."
  ]
}
```

The `hours` array must contain exactly 24 entries:

```
hour 0 through hour 23
```

Each entry contains:

```json
{
  "hour": 0,
  "demand_kwh": 50,
  "solar_kwh": 0,
  "tariff_bdt_per_kwh": 8
}
```

# Response

The API returns:

- Scenario ID
- Directive interpretation
- Optimized 24-hour schedule
- Total grid usage
- Total energy cost
- Peak grid usage
- Summary of the plan

Example:

```json
{
  "scenario_id": "campus_demo_001",
  "directive_interpretation": [],
  "hourly_plan": [],
  "total_grid_kwh": 500,
  "total_cost_bdt": 4000,
  "peak_grid_kwh": 80,
  "plan_summary": "Optimized energy schedule generated."
}
```

---

# Optimization Model

The optimizer minimizes:

```
Total Cost =
Σ(Grid Energy Used × Electricity Tariff)
```

while satisfying:

- Energy balance constraints
- Battery capacity limits
- Minimum battery reserve
- Maximum charging rate
- Maximum discharge rate
- Solar availability
- Operator directives
- End-of-day battery neutrality

The battery returns to its initial energy level after the 24-hour optimization period.

---

# LLM Integration

The LLM component performs:

- Natural language understanding
- Operator note classification
- Time window extraction
- Parameter extraction

The output is validated before entering the optimizer.

Validation checks:

- Allowed directive types
- Valid time ranges
- Numeric limits
- Correct structured adjustment format
- Invalid outputs safely converted to `no_op`
